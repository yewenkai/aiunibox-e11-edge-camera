# RK3566 NPU 轻量视觉路线

## 目标与边界

目标是在不影响 30fps 采集和推流稳定性的前提下，利用 RK3566 约 1 TOPS NPU 完成低频率、轻量化、本地运行的视觉判断。

项目不做人脸身份或年龄识别，不把 NPU 框烧进视频，也不把视频上传到云端。可选的“面部可见性”只在已有姿态风险候选时分析头部裁剪区域，既不比对身份也不保存裁剪图。动作、哭声或用户主动打开后的姿态事件可以按明确容量上限在设备端保存短片，详见 [EVENT_TIMELINE.md](EVENT_TIMELINE.md)。

## 推荐数据流

```text
Camera2
  ├─ Surface -> MediaCodec -> RTSP/WebRTC
  └─ ImageReader -> 降采样/限频 -> NPU Worker -> 事件状态
```

分析链路必须和编码链路解耦：

- 编码继续使用 Surface 零拷贝，不因视觉算法改回 CPU 全帧转换。
- ImageReader 使用独立低分辨率输出，队列深度保持 1，只处理最新帧。
- 初始分析频率建议 2～5fps；无人时可进一步降频。
- NPU Worker 不允许阻塞 Camera2 回调线程。

## 阶段 1：有人/无人

输入建议从 320×320 或更低分辨率开始，选择许可证清晰、可转换到 RKNN 的轻量检测模型。

输出：

- `personPresent`
- `confidence`
- `lastSeenAt`
- 可选的人体框；默认不持久化

验收重点：

- 摄像头推流帧率基本不受影响
- 连续运行稳定
- 逆光、夜视、局部遮挡下可接受
- 有明确的误报/漏报统计，而不是只展示单次演示

### 当前实现（实验性）

- 模型：Rockchip RKNN Model Zoo 优化版 YOLOv8n，640×640 输入，RK3566 INT8。
- 运行：APK 可选加载 RKNN Runtime 2.3.0，通过 JNI 调用设备 NPU；日常每 2 秒复用一张 JPEG 快照。动作或哭声触发时，常规轮询会主动让路，新帧子预算为 180ms、取帧与推理总预算为 450ms；不足 0.5 秒的刚完成结果可由并发信号复用，避免重复排队。
- 后处理：按 3 个尺度的 box/class/score-sum 共 9 路输出解码 DFL，只保留 person 类并做 NMS。
- 防抖：最近 3 帧至少 2 帧命中后进入“有人”，连续 10 秒未命中后退出。
- 陪护状态：当前帧一旦检出两人或成人体型证据，就即时抑制当次 Bark；最近 4 次中
  至少 3 次出现这些证据后，稳定判定“有人陪护”。
  陪护证据消失约 20 秒后恢复通知；若被压制的哭声或动作仍持续，会重新评估原事件会话。UNKNOWN 和视觉漏检都保持通知武装。
- 成人体型：以现场校准门槛为基准，按人体框底部位置有限补偿远处目标的透视缩小；它仍不是年龄分类。
- 降级：缺少 SDK 头文件、运行库或模型时，普通摄像头版本仍可构建和运行。
- 现场校准：页面可让画面中只保留一名成人，在常见陪护位置收集 8 次人体框比例。只落盘中位高度、面积和带余量的启发式阈值，不保存截图或身份。

真机 RK3566 / Android 11 上已验证模型初始化和持续推理，稳定单帧约 90～125ms，
GPU 时间戳合成和 H.264 推流同时运行约 30fps。通用 person 模型对“侧卧且被褥大面积
遮挡”的场景存在明显漏检，因此 UI 只陈述“检出人体 / 未检出人体”，不能把后者解释为
确定无人。当前 NPU 结果只作为守护上下文，不作为动作检测或哭声检测的硬开关：即使
暂未检出人体，这两条守护链路也会继续运行，避免因遮挡漏检造成监护空窗。COCO person
类别只能说明画面中检出通用人体，不能据此判断目标是宝宝还是成人。

当前逻辑不要求宝宝位于婴儿床，也不依据重点区域内外位置推断身份。重点区域只供
`MotionDetector` 计算帧差，NPU 始终使用全画面人数和人体框尺寸寻找成人陪护证据。
成人体型证据不是年龄分类；兄弟姐妹、访客、近距离宝宝、镜面反射或固定阈值都可能
造成误判，不能作为医疗或人身安全系统的唯一依据。

动作、哭声以及陪护状态变化会进入事件解释时间线。动作和哭声触发时复用 H.264 主链路
保存事件前约 10 秒、后约 20 秒的端侧 MP4；NPU 框不写入视频。短片数量、容量、手动
删除和 iOS Range 播放规则见 [EVENT_TIMELINE.md](EVENT_TIMELINE.md)。

### 自行转换与部署

仓库仅提供 `scripts/convert_yolov8_rknn.py`，不分发 SDK、运行库、模型、校准图或家庭画面。

1. 在 Rockchip 支持的 Linux x86_64 环境安装 RKNN Toolkit 2，并从官方 Model Zoo 取得优化版 YOLOv8n ONNX。
2. 准备已授权、已清理隐私的校准图片列表，运行：

   ```bash
   python scripts/convert_yolov8_rknn.py \
     --onnx /path/to/yolov8n.onnx \
     --dataset /path/to/dataset.txt \
     --output /path/to/yolov8n_rk3566.rknn
   ```

3. 自行取得与设备兼容的 `rknn_api.h` 和 Android arm64 `librknnrt.so`，分别放到
   `android-app/app/src/main/cpp/` 与 `android-app/app/src/main/jniLibs/arm64-v8a/` 后编译 APK。
4. 把模型放入应用私有目录，文件名必须为 `yolov8n_rk3566.rknn`。模型、运行库、
   SDK 头文件和校准数据均已被 `.gitignore` 排除。

如果希望让 Codex 检查本机环境并逐步指导上述流程，请使用
[SELF_BUILD_WITH_CODEX.md](SELF_BUILD_WITH_CODEX.md) 中的提示词。Codex 只能协助执行和
核对，第三方许可证与设备使用授权仍需由使用者确认。

## 睡姿补强的四步门控（均已实现）

1. Pose 影子模式只记录姿态、关键点有效率和耗时，先连续观察至少 24 小时，默认不通知。
2. 浏览器显示姿态卡片，并可选临时调试骨架；骨架默认关闭且不进入任何编码画面。
3. 用户可反馈“判断正确 / 错误”；实验性姿态通知仍是独立开关，默认关闭，建议观察若干昼夜后再启用。
4. 面部可见性模型仅在已有风险候选时按需分析头部裁剪，平时不运行。

## 阶段 2：睡姿 Pose 影子模式（已实现，默认关闭）

- 模型：Rockchip Model Zoo 的 YOLOv8n-Pose 转换路线，640×640、RK3566 INT8、17 个 COCO 关键点。
- 调度：每 2 秒复用最近 JPEG，与人体模型共用进程级 NPU 执行锁，避免两个 `rknn_run` 并发争用单核 NPU。
- 后处理：解码 3 个 `65×H×W` 分支和 17×3×8400 关键点输出，做 DFL、person sigmoid、NMS 和 letterbox 反变换。
- 标签：脸部关键点可见性与肩髋几何只形成“疑似仰卧 / 侧卧 / 俯卧 / 不明确”影子标签；最近 6 次至少 5 次一致才更新稳定状态。
- 统计：`files/pose-diagnostics/rolling-24h.json` 按分钟聚合样本数、有效率和耗时，不保存截图或原始关键点历史。
- UI：网页姿态卡片显示稳定/原始标签、关键点有效率和耗时；调试骨架默认关闭，只在浏览器 canvas 临时绘制。
- 目标连续性：多人时优先跟随与上一帧重叠的人体框，连续 3 次漏检后才清空；失配时才回退到较小非成人体型候选。
- 反馈：页面可对最近结果标记“判断正确 / 错误”，只供人工复盘，不自动学习。
- 通知：独立开关默认关闭，并有 5 分钟冷却；外发前补跑一次人体 NPU，两人、成人体型或陪护缓冲证据始终优先抑制通知；成人离开且风险持续时重新评估。
- 冒烟：受 API 鉴权保护的 `/api/pose-selftest` 只运行一帧，不启动动作/哭声、不通知，也不计入 24 小时样本，供安装模型后核对 RKNN 契约。

## 阶段 3：风险时按需面部可见性（已实现，默认关闭）

- 模型：RetinaFace mobile320，320×320、RK3566 INT8。
- 只有 Pose 原始标签进入俯卧/侧卧风险候选时才估计头部区域和运行模型，平时不推理。
- 头部区域优先使用可见鼻眼耳中心；脸部关键点缺失时，以肩部中点背离髋部中点的方向粗估。
- 当前只读取 4,200 个先验框中的最高 face 分数，输出“可见 / 未确认可见”附加证据，不做身份识别，也不把结果当作通知的唯一条件。
- 关闭该开关时立即释放 RetinaFace context；关闭 Pose 或视觉守护时同时释放全部新增 context。

## 阶段 4：简单手势（后续候选）

建议采用两阶段轻量方案：

1. 手掌或手部区域检测
2. 对裁剪区域做少量静态手势分类

先支持 3～5 个差异明显的静态手势，避免一开始处理复杂动态轨迹。手势只触发本地动作，并增加持续时间、置信度和冷却时间，防止误触。

## 工具链与许可证

- RKNN Toolkit / Runtime 应由使用者从 Rockchip 官方渠道取得。
- 模型转换脚本可以开源，但不要把来源和许可证不清晰的模型权重提交到仓库。
- 每个模型都应记录来源、许可证、输入尺寸、量化方式和精度评估。
- 数据集涉及家庭场景时，应先做隐私清理并取得被拍摄者授权。

## 建议里程碑

1. 建立不接模型的抽帧和性能测量骨架。
2. CPU 上跑通一个许可证清晰的基线模型。
3. 转换 RKNN 并验证输出一致性。
4. 接入 NPU Runtime，记录时延、CPU、内存和可用的设备健康信号；当 Thermal HAL 不可用时明确标记，不伪造温度结论。
5. 与推流并行运行 24 小时稳定性测试。
6. 再接事件通知或手势控制。
